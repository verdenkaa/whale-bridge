# Архитектура

Whale Bridge — приложение на Electron: главный процесс владеет окном, диском и
привилегированными операциями, интерфейс рисует состояние и ничего не пишет
напрямую, а страница DeepSeek живёт в отдельном изолированном webContents.

## Процессы и окна

```text
main.js — главный процесс
├── BrowserWindow (интерфейс Whale Bridge)
│     ├── preload-ui.js   — белый список IPC (contextBridge, window.api)
│     └── ui/index.html   — интерфейс: панели, редактор Monaco, терминал xterm.js
├── WebContentsView (чат DeepSeek, partition «persist:deepseek»)
│     └── preload-chat.js — наблюдатель DOM: только чтение, отправка блоков кода
└── popup-окна авторизации (та же сессия, что у чата)
```

- **Главный процесс** (`main.js`): окно и геометрия, локальное хранилище, файловые
  операции, предложения модели, оркестратор запуска, IPC. Все привилегированные
  действия — только здесь.
- **Renderer интерфейса** (`ui/`): sandbox + contextIsolation, Node-API нет, весь
  доступ к миру — через `window.api` (preload-ui.js). Состояние интерфейса живёт
  в `ui/app.js` (объект `S`), состояние открытых файлов — в `ui/editor-state.js`
  (чистые функции).
- **Страница DeepSeek** (`WebContentsView`): официальный сайт в своём partition,
  cookies переживают перезапуск. `preload-chat.js` только читает DOM (блоки `pre`)
  и отправляет «дозревшие» блоки в main; никакие API страницы он не трогает и
  ничего не отправляет в чат от имени пользователя.

Главное окно и чат — разные webContents в одном окне приложения. Чат физически
размещается в пустом контейнере `#chat-slot`: renderer измеряет его
`ResizeObserver` и присылает прямоугольник (`chat:set-bounds`), main кладёт туда
`WebContentsView`. Геометрию считает интерфейс, main её не изобретает.

## Карта модулей

### Главный процесс и общее ядро (`src/`)

| модуль | роль |
|---|---|
| `paths.js` | нормализация относительных путей и `resolveInProject`: проверки на `..`, абсолютные пути, зарезервированные имена Windows, `.git`, побег через символические ссылки (realpath ближайшего существующего предка) |
| `fileops.js` | чтение/запись файлов: единственная точка записи `applyChange` (create/update/delete/move), атомарная запись, резервные копии, откат `restore`, дерево проекта, индексы и отпечатки диска |
| `treefs.js` | операции пользователя из дерева (создать/переименовать/удалить) поверх `fileops.applyChange` + перенос журнала контекста при переименовании |
| `editorfs.js` | чтение и запись из редактора: проверка `expectedHash`, конфликт сохранения (§11) |
| `store.js` | локальное хранилище: config.json, history.json, резервные копии, снимки контекста, базовые снимки; очередь атомарной записи |
| `proposals.js` | жизненный цикл предложений: ingest, дедупликация, оценка (diff, состояния), apply/merge/reject/dismiss, история, журнал контекста, отчёты |
| `parser.js` | разбор блока кода: маркер `&путь`, `&NEW:`, `&DELETE:`, `&MOVE:`, `&RUN:`, `&CMD:`, эвристики неполного ответа |
| `patch.js` | SEARCH/REPLACE и REPLACE_BLOCK: разбор, допуски (пробелы/отступы), поиск функции по заголовку |
| `diff.js` | построчный diff (Майерс, деградация при >3000 различий), unified diff |
| `hunks.js` | ханки предложения и трёхстороннее слияние `merge3` |
| `versions.js` | модель версий файла: aiBase / disk / saved / editor, классификация состояний |
| `context.js` | правила журнала контекста: запись знания, расхождения, невиденные файлы, лимиты |
| `promptgen.js` | конструктор промпта: секции, пресеты, текстовое дерево, памятка формата |
| `runlangs.js` | таблица языков запуска, планы (`planRun`, `planShell`), разбор аргументов, классификатор опасных команд |
| `runsettings.js` | модель представления «Настройки → Запуск»: строки таблицы, статусы, правило правки config.run |
| `toolchain.js` | автопоиск инструментов в PATH, версии (`--version`), ручные пути, кеш до смены конфига |
| `runner.js` | оркестратор сессий запуска: шаги плана, pty, watchdog, лимиты вывода и ввода, отчёт |
| `runfmt.js` | очистка вывода от ANSI, сборка отчёта для чата, кольцевой буфер |

### Интерфейс (`ui/`)

| модуль | роль |
|---|---|
| `app.js` | состояние `S`, панели и режимы, карточки предложений, события запуска, конструктор промпта, настройки |
| `editor.js` | Monaco: вкладки, дерево файлов, оверлеи (конфликт, быстрый поиск), DiffEditor, контекстное меню |
| `editor-state.js` | чистая логика состояния открытых файлов (dirty/drift/missing, pendingAi) |
| `terminal.js` | xterm.js + addon-fit: singleton, ввод (`run:input`), размер (`run:resize`), буфер до монтирования |
| `monaco.js` | локальная загрузка AMD-сборки Monaco, язык по расширению |
| `layout.js` | математика раскладки (общая с main): sanitize, drag, normalizeRect |
| `dom.js` | `h()`: создание DOM только через textContent — innerHTML с чужими данными запрещён |
| `languages/gdscript.js` | подсветка GDScript (Monarch) |

### Общие модули (UMD)

Часть модулей написана как UMD и подключается и в main (require), и в renderer
(script tag): `versions.js`, `context.js`, `diff.js`, `hunks.js`, `runlangs.js`,
`runsettings.js`, `ui/layout.js`. Причина: правило должно быть одно на два
процесса. Две реализации «что значит расхождение» или «как экранировать команду»
рано или поздно разошлись бы, а расхождение в таких правилах — это либо ложная
тревога, либо молча уехавший контекст.

## Потоки данных

### Предложение модели: от страницы до диска

```text
DeepSeek печатает блок кода
  → preload-chat.js: MutationObserver + таймер; блок «дозрел» (текст не менялся 1.2 с)
  → chat:blocks (пакетами не больше 100) → main: проверка отправителя, хоста и структуры
  → proposals.ingest: parser.parseBlock → маркер + режим (full/patch)
      дедупликация по contentHash, память решений (applied/rejected/dismissed/executed)
  → sealAiBase: печатает aiBaseHash — версию файла на диске в момент появления блока
  → renderer: proposals:list → карточки; proposal:get → оценка + diff
  → «Принять»: proposal:apply → fileops.applyChange (хэш, бэкап, атомарная запись)
      → история + журнал контекста («модель знает эту версию»)
  → или принятие по ханкам в буфер редактора → Ctrl+S → file:write (тот же applyChange)
```

Ключевые инварианты:

- **Единственный путь записи** файла проекта — `fileops.applyChange`: и предложение
  модели, и сохранение из редактора, и операции дерева идут через него (проверка
  пути, проверка SHA-256, резервная копия, атомарная замена, запись в историю).
- **Ничего не пишется без подтверждения**: сам факт разбора блока ничего не меняет.
- **Дедупликация по содержимому**: отпечаток предложения — хэш от (чат, операция,
  путь, содержимое), поэтому догрузка старых сообщений чата не воскрешает
  отработанные карточки.

### Запуск файла или команды

```text
F5 / «▶ Запустить» / карточка &RUN:/&CMD:
  → сохранение dirty-буферов (file:write)
  → run:start → runner.start: sanitize конфига → toolchain.detect (кеш)
      → runlangs.planRun (шаги: build → run) или planShell (&CMD:)
  → spawnPty (node-pty адаптер) → run:data / run:exit / run:state → терминал
  → кольцо вывода 4 МБ, watchdog бездействия, журнал ввода с лимитом
  → «📋 Отчёт» → runfmt.buildReport → буфер обмена → вставка в чат
```

Подробности — в [Терминал и запуск](run.md).

### Слежение за диском

`fs.watch` на папке проекта (рекурсивный, с фильтром служебных папок и дебаунсом
300 мс) шлёт `files:changed`; renderer перечитывает дерево, хэши открытых файлов
и журнал контекста. На время сессии запуска наблюдатель приостанавливается
(компиляция создаёт файлы в `.ide_build`) и гарантированно возобновляется по
завершении. Запасной путь — инвалидация кешей при фокусе окна.

## Локальные данные

Всё живёт в `userData` приложения (Electron), на сервер ничего не уходит:

| путь | содержимое |
|---|---|
| `config.json` | проекты, привязки чатов (`sessions`), раскладка, `config.run` (инструменты, аргументы, таймаут), черновик промпта и пресеты, исключения дерева, решения по предложениям, журнал контекста (`contextKnown`, `contextSeen`) |
| `history.json` | журнал операций (лимит 1000 записей; вытеснённые записи удаляют свои резервные копии) |
| `backups/` | резервные копии `<opId>.before` / `<opId>.after`; хранятся 2 последние версии файла (pruneFile) |
| `context/` | снимки версий, которые видела модель; адресация по SHA-256 содержимого, лимит ~300 файлов и ~1 МБ текста на снимок |
| `baselines.json` | базовые снимки пар чат+проект («размер:mtime:хэш» на файл) для слежения за невиденными файлами |

Запись конфигурации и журнала — через очередь (`store._write`): tmp-файл +
rename, последовательно, поэтому конфигурация не бьётся даже при частых
сохранениях.

## IPC

Три класса каналов (полные белые списки — в `preload-ui.js`, сверяются тестами
`tests/wiring.test.js` и `tests/ipc-channels.test.js`):

- **invoke** (`api.invoke`) — запрос/ответ: состояние, проекты, файлы,
  предложения, история, контекст, промпт, запуск, настройки. Каждый обработчик в
  main проверяет `event.sender === win.webContents`: страница DeepSeek не может
  вызвать привилегированные каналы, даже если получит доступ к `window.api`
  (у неё его нет — preload другой).
- **send** (fire-and-forget) — то, что не должно ждать round-trip: геометрия чата
  (`chat:set-bounds`, каждый кадр перетаскивания) и ввод терминала (`run:input`,
  `run:resize`).
- **events** (main → renderer) — `chat:changed`, `proposals:changed`,
  `projects:changed`, `files:changed`, `project:auto-bound`, `run:data`,
  `run:exit`, `run:state`.

Отдельный вход — `chat:blocks` от preload-chat.js: принимается только от
webContents чата и только когда кадр принадлежит `deepseek.com`; структура
payload проверяется жёстко (формат chatId, лимиты размеров и числа блоков).

Payload из renderer считается недоверенным и чистится на входе
(`cleanAiAccepts`, `sanitizeSections`, `sanitizeRunConfig`, `layoutMath.sanitize`
и т.д.) — так же строго, как данные со страницы чата.

## Раскладка и режимы панелей

- Раскладка (ширины панелей, высота терминала, активная вкладка, открытость
  «Промпта») — данные в `config.json`; математика — `ui/layout.js` (UMD, общая с
  main: sanitize сохранённых значений и нормализация прямоугольника чата).
- Центральная панель показывает ровно одно: код (Monaco), «Промпт», «Настройки»
  или просмотр (DiffEditor/отчёт). Monaco и DiffEditor создаются один раз и
  переживают перерисовки — пересоздание редактора сбрасывало бы вид и курсор.
- Терминал — нижняя панель колонки редактора, независим от режима центра.

## Тесты и проверяемые контракты

- Логика (src/, editor-state, layout, hunks, diff, runlangs…) покрыта node-тестами
  на чистых функциях и DI-фейках (runner — на фейковом pty, toolchain — на
  фейковом execFile, store — на временной папке).
- `tests/wiring.test.js` и `tests/ipc-channels.test.js` разбирают main.js и
  преагрузчики как текст и сверяют белые списки каналов с фактическими
  вызовами: канал, который разрешил preload, но не слушает main (или наоборот),
  не доедет до рантайма — тест упадёт раньше.
- `tests/ui-smoke.test.js` прогоняет app.js и terminal.js на минимальной имитации
  DOM без Electron: связи «кнопка → IPC → перерисовка» покрыты.
- `tests/source-hygiene.test.js` — гигиена исходников: LF в индексе git, отсутствие
  посторонних письменностей, NUL-байтов, отладочного кода и смешения письменностей
  внутри слова.

Подробнее — в [Сборка и тесты](build-and-test.md).
