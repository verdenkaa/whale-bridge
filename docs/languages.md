# Поддержка языков: как устроена и как расширить

Языки запуска — **данные, а не код**: таблица `LANGS` в `src/runlangs.js` (UMD,
общая для main и renderer). Добавить язык — значит дописать один объект-дескриптор
и, при необходимости, пару строк в соседние таблицы. Специальная логика в раннере
появляется только для языков с нестандартной подготовкой (как C# со служебным
`.csproj`).

## Дескриптор языка

```js
// src/runlangs.js, таблица LANGS
Object.freeze({
  id: 'python',            // идентификатор (план, настройки, отчёты)
  label: 'Python',         // подпись для интерфейса
  exts: Object.freeze(['.py']),  // расширения файлов (с точкой, нижний регистр)
  tools: Object.freeze([Object.freeze({
    key: 'python',         // ключ инструмента: ручной путь в config.run.tools
    names: Object.freeze(['python', 'python3', 'py']), // кандидаты для поиска в PATH (порядок значим)
    label: 'Python',       // подпись инструмента в таблице настроек
    install: 'Python 3 и добавьте его в PATH (или укажите путь к python.exe вручную)',
  })]),
  plan: ({ rel, args, exeSuffix }) => ({
    steps: [{ kind: 'run', tool: 'python', exeSuffix, args: ['-u', rel, ...args] }],
    env: { PYTHONPATH: '{root}', PYTHONIOENCODING: 'utf-8' },
  }),
}),
```

Поля плана:

- `plan(ctx)` — **чистая функция**: ничего не проверяет на диске и не ищет
  инструменты, только собирает шаги. Контекст: `rel` (путь файла от корня),
  `base` (имя без расширения), `ext`, `args` (дополнительные аргументы из
  настроек), `exeSuffix` (`.exe` на win32, пусто иначе), `platform`, `fqcn`
  (Java), `nodeMajor`, `csharp`.
- `steps[]` — `{kind: 'build' | 'run', tool?, exe?, args}`. `tool` — шаг
  исполняется найденным инструментом (ключ из `tools`); `exe` — литеральный
  исполняемый файл шага (например, собранный бинарник `.ide_build/app`). Наличие
  хотя бы одного шага `build` заставляет раннер создать папку артефактов
  (`.ide_build` + суффикс языка, как `/classes` у Java и `/bin` у C#).
- `env` — переменные окружения процесса; `{root}` заменяется на корень проекта.

Двухшаговый пример (компиляция → запуск):

```js
plan: ({ rel, base, args, exeSuffix }) => ({
  steps: [
    { kind: 'build', tool: 'cpp', args: [...args, rel, '-o', BUILD_DIR + '/' + base + exeSuffix] },
    { kind: 'run', exe: BUILD_DIR + '/' + base + exeSuffix, args: [] },
  ],
  env: null,
}),
```

Порядок шагов в терминале: провал компиляции (ненулевой код) останавливает сессию,
успех — разделитель `── запуск ──` и второй шаг в том же терминале.

## Чек-лист добавления языка

1. **`src/runlangs.js`**
   - дескриптор в `LANGS` (id, label, exts, tools, plan);
   - новый ключ инструмента — в `TOOL_KEYS` (по нему живут ручные пути в
     `config.run.tools`; `sanitizeRunConfig` чистит конфиг строго по этому списку);
   - нужны дополнительные аргументы — ключ в `ARGS_KEYS` (`config.run.args`).
     Определите, куда план их вставляет: у компиляторов — перед `-o`/`-d`, у
     интерпретаторов и программ — в конец;
   - `BUILD_DIR` (`/classes`, `/bin`) для артефактов — в `planRun` (`outSub`).
2. **`src/runsettings.js`** — подсказка к полю аргументов в `ARG_HINTS` (если язык
   в `ARGS_KEYS`). Строки таблицы инструментов, статусы и подсказки «что
   установить» строятся из дескрипторов `LANGS` автоматически — отдельной таблицы
   языков в настройках нет.
3. **`ui/monaco.js`** — расширение → язык подсветки в карте `BY_EXT` (для файлов,
   открытых в редакторе; Monaco сам сопоставляет расширения встроенным языкам,
   карта нужна для буферов без URI). Своей подсветки нет — добавьте Monarch-файл
   в `ui/languages/` по образцу `gdscript.js` и зарегистрируйте его в
   `ui/monaco.js` (init) + подключите script в `ui/index.html`.
4. **Тесты** (без них CI не пройдёт):
   - `tests/runlangs.test.js` — план нового языка (шаги, аргументы, env,
     поведение на win32/posix);
   - `tests/runsettings.test.js` — строки таблицы и `nextConfig` для нового ключа;
   - `tests/runner.test.js` — сессия запуска на фейковом тулчейне (инструмент
     найден / не найден / битый ручной путь);
   - `tests/wiring.test.js` сверяет связанность (как в приёмке C#: язык,
     инструмент и служебные файлы видны на всех сторонах) — добавьте аналогичную
     проверку, если язык вводит новые сущности.

## Что происходит автоматически

Добавлять код в раннер, настройки или интерфейс **не нужно**:

- **поиск инструмента**: `toolchain.detect` проходит `LANGS` → `tools` и ищет
  каждого кандидата в PATH (Windows: `PATHEXT`, текущая папка, регистронезависимые
  переменные окружения), проверяет ручной путь из `config.run.tools[key]` и снимает
  версию (`--version`, таймаут 3 с). Ручной путь побеждает; битый ручной путь —
  честный отказ запуска, а не молчаливая подмена. Для Python есть особое
  предпочтение major 3 (`pickPreferred`) — единственный языко-специфичный нюанс
  поиска;
- **карточки &RUN:**: язык предложения определяется по расширению
  (`runlangs.langByExt`) в `proposals._evaluateRun` — новое расширение
  автоматически становится запускаемым из чата;
- **таблица настроек**: строки, статусы (`✔ найден`, `⚠ указан, но не найден`,
  `✘ не найден в PATH`) и сообщения «что установить» (`missingToolMessage`)
  строятся из дескрипторов;
- **отчёт и терминал**: короткие имена инструментов, разделители фаз и код
  возврата не зависят от языка.

## Особые случаи (когда чистой таблицы мало)

- **C#**: до плана раннер выполняет `prepareCsharpProject` — ищет пользовательский
  `.csproj` (в ширину, до 4 уровней) или создаёт служебный `.ide_build/app.csproj`
  (шаблон `csharpProjectXml`, `TargetFramework` по мажорной версии SDK). Результат
  приходит в план через `ctx.csharp = {proj, assembly}`; без него план C# честно
  отказывается строиться. Это единственный язык с подготовкой на диске.
- **Java**: полное имя класса (`package x.y;` + имя файла) разбирается из
  исходника (`javaClassFqn`) и приходит через `ctx.fqcn`.
- **TypeScript**: план фильтрует `--experimental-strip-types` по `nodeMajor`
  (флаг нужен только Node 22.x); версия node снимается до построения плана.

Если новому языку нужна подобная подготовка, добавляйте её в
`runner.prepareFilePlan` (до создания сессии, чтобы старая сессия не убивалась
зря), а не в чистый план.

## Соглашения

- Дескрипторы и вложенные массивы — `Object.freeze`: таблица общая на два
  процесса, случайная мутация в одном не должна быть видна в другом.
- Всё платформенное (`exeSuffix`, разделители путей, оболочка) приходит из
  контекста плана, а не читается из `process.platform` по месту: тесты внедряют
  целевую платформу и обязаны получать её поведение на любой хост-машине.
- Правила одни на два процесса: renderer рисует бейджи и таблицу настроек ровно
  тем, что возвращают `runlangs`/`runsettings` (UMD), а не своей копией.
