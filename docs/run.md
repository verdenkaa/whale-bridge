# Терминал и запуск

Как устроен запуск файлов и команд: планы, поиск инструментов, оболочка, ограничения
и кодировки. Пользовательская часть (кнопки, панель, отчёт) — в
[Руководстве пользователя](usage.md#терминал).

## Общая схема

```text
ui/app.js ──run:start──▶ main.js ──▶ src/runner.js (оркестратор сессий)
                                        │  план: src/runlangs.js (planRun / planShell)
                                        │  инструменты: src/toolchain.js (detect, кеш)
                                        ▼
                                   node-pty (spawnPtyAdapter)
                                        │
   терминал (ui/terminal.js, xterm.js) ◀─┴─ run:data / run:exit / run:state
        ввод: run:input, размер: run:resize (fire-and-forget, без round-trip)
```

Раннер не зависит от Electron и node-pty напрямую: pty, kill дерева, часы, fs и
платформа внедряются через DI, поэтому весь жизненный цикл сессии покрыт
node-тестами на фейковом pty (`tests/runner.test.js`).

Одна активная сессия: новый запуск при работающем процессе — это перезапуск
(предыдущий убивается автоматически). Запуск **не трогает** журнал контекста и
историю операций: это чтение мира, а не изменение проекта. Единственная запись на
диск — папка `.ide_build/` (артефакты сборки и служебный `app.csproj`).

## Планы запуска

План — чистая функция `runlangs.planRun(langId, rel, opts)`: шаги
`{kind: 'build' | 'run', tool?, exe?, args}`, переменные окружения и папка
артефактов. Интерпретируемые языки — один шаг, компилируемые — два (компиляция →
запуск бинарника в том же терминале, между ними разделитель `── запуск ──`;
провал компиляции останавливает сессию).

| язык | расширения | как запускается |
|---|---|---|
| Python | `.py` | `python -u файл` (кандидаты PATH: `python`, `python3`, `py`; предпочитается Python 3) |
| JavaScript | `.js` `.mjs` `.cjs` | `node файл` |
| TypeScript | `.ts` `.mts` | `node --experimental-strip-types файл` (нужен Node.js 22 или новее) |
| C++ | `.cpp` `.cc` `.cxx` | `g++ файл -o .ide_build/имя` → `.ide_build/имя` (кандидаты: `g++`, `clang++`) |
| C | `.c` | `gcc файл -o .ide_build/имя` → `.ide_build/имя` (кандидаты: `gcc`, `clang`) |
| Java | `.java` | `javac -encoding UTF-8 -d .ide_build/classes файл` → `java -cp .ide_build/classes класс` |
| C# | `.cs` | `dotnet build проект.csproj --configuration Release -o .ide_build/bin` → `dotnet .ide_build/bin/сборка.dll` |

Детали:

- cwd всегда корень проекта, поэтому в терминале и отчёте пути короткие.
- Исполняемый файл шага с каталогом в пути (`.ide_build/app.exe`) делается
  абсолютным: на Windows CreateProcess ищет относительный путь относительно папки
  РОДИТЕЛЯ (Electron), а не переданного cwd.
- Окружение: копия `process.env` плюс подстановки плана (у Python —
  `PYTHONPATH={root}` и `PYTHONIOENCODING=utf-8`; `{root}` заменяется на корень
  проекта). Папки инструментов, указанных в настройках вручную, добавляются
  **в начало** `PATH` процесса (регистр имени переменной находится без учёта
  регистра: в Windows она обычно `Path`): собранному MinGW-бинарнику нужны DLL
  рядом с компилятором, а `javac` — свои классы из JDK. Системный `PATH` не меняется.
- Флаг Node `--experimental-strip-types` планируется только для Node 22.x: на 23+
  TypeScript исполняется нативно, на более старом — честная ошибка «нужен Node.js 22
  или новее» вместо загадочного SyntaxError.
- Полное имя Java-класса (`package x.y;` + имя файла) разбирается из исходника.
- Артефакты сборки складываются в `.ide_build/` — папка входит в
  `fileops.IGNORE_DIRS`, поэтому не видна ни дереву файлов, ни промпту, ни слежению
  за невиденными файлами.

### C#: поиск или создание проекта

Перед сборкой раннер ищет пользовательский `.csproj` (обход в ширину от корня, не
глубже 4 уровней, служебные папки пропускаются). Проектов несколько — берётся самый
мелкий, затем первый по алфавиту: выбор детерминированный. Если своего `.csproj`
нет, в `.ide_build/app.csproj` создаётся **служебный минимальный проект**
(консольное приложение, `AssemblyName` = `app`, `EnableDefaultItems` выключен,
исходники — glob всех `.cs` из корня проекта без `bin`/`obj`/`.ide_build`/`.git`/
`node_modules`), поэтому одинокий `Program.cs` запускается без ручного создания
проекта. `TargetFramework` — по мажорной версии найденного SDK (`net9.0` на SDK 9):
совпадающая версия собирается без restore из сети. Служебный проект создаётся один
раз и не перезаписывается — его можно поправить руками (например, добавить пакет).

## Поиск инструментов (toolchain)

`toolchain.detect(config.run)` по каждому инструменту:

1. **Ручной путь** из настроек побеждает автопоиск. Относительный путь
   разрешается правилами целевой платформы. Путь перестал существовать —
   `brokenManual`: запуск честно отказывает («указан, но не найден»), а **не**
   молча подменяет ваш выбор другим интерпретатором из PATH.
2. **Автопоиск в PATH** по списку кандидатов дескриптора (порядок сохраняется).
   На Windows учитываются `PATHEXT` и поиск в текущей папке (как это делает
   cmd.exe), регистр переменных окружения не важен.
3. **Версия** — `--version` с таймаутом 3 секунды (вывод бывает и в stderr).
   Для Python важен major: если среди кандидатов есть третья версия, берётся она,
   иначе честный первый (системный `python` до сих пор бывает вторым).

Результат кешируется до изменения `config.tools`; кеш сбрасывается перед каждым
запуском (инструмент могли установить, не трогая настройки), по кнопке «↻ Обновить»
и при сохранении настроек.

## Команды модели (&CMD:) и оболочка

`runlangs.planShell(command, platform)` — чистая функция:

- POSIX: `/bin/sh -c команда` (аргументы массивом).
- Windows: `cmd.exe /d /s /c «chcp 65001>nul & команда»`, `ComSpec` подставляется
  из окружения (надёжнее поиска `cmd.exe` в PATH).

Два неочевидных решения Windows:

1. **verbatim**: команда оболочки уходит в node-pty ОДНОЙ СТРОКОЙ. Из массива
   node-pty собирает командную строку по правилам MSVCRT (кавычка внутри аргумента
   превращается в `\"`), а cmd.exe такое экранирование не понимает:
   `findstr "fn main" poem.rs` доезжал как `findstr fn main poem.rs` и падал.
   Строку node-pty кладёт в командную строку дословно.
2. **chcp 65001**: консоль cmd.exe по умолчанию в OEM-кодировке (в России CP866),
   а файлы проекта Whale Bridge пишет в UTF-8. Префикс переводит консоль в UTF-8
   до выполнения команды, `>nul` прячет ответ chcp. В отчёте и в карточке префикс
   не показывается: там команда ровно та, что предложила модель.

PowerShell намеренно не внедряется — оболочка зафиксирована на cmd.exe (решение
пользователя, ТЗ §5.3).

### Кириллица в командах (Windows)

Командная строка доезжает до `cmd.exe` в Unicode, кириллица в ней цела. Но есть два
независимых участка, где старые консольные утилиты всё равно ненадёжны:

**1. Не-ASCII символы в АРГУМЕНТАХ** (`findstr`, `sort`, `more`, `fc`) до них не
доходят: такие утилиты разбирают свои аргументы в системной кодировке Windows
(CP1251/CP866), а не в UTF-8. В итоге `findstr /c:"Светит" poem.rs` отвечает «не
найдено», хотя строка в файле есть, — а `findstr /c:"fn main"` с латиницей
работает. `chcp` здесь бессилен: он меняет кодовую страницу консоли, а не
кодировку аргументов процесса.

Рабочий способ — PowerShell: он читает файл в UTF-8 сам и не зависит от кодировки
консоли. Модель знает это правило (пункт 15 в «Правилах работы») и предлагает такие
команды сама; вручную команда выглядит так:

```text
powershell -NoProfile -Command "Get-Content poem.rs -Encoding UTF8 | Select-String 'Светит'"
```

Образец — в одинарных кавычках внутри двойных. Тот же эффект даёт общесистемная
настройка Windows «Beta: Use Unicode UTF-8 for worldwide language support»
(системная кодировка становится 65001) — с ней и `findstr` находит кириллицу, но
менять её ради одного приложения не нужно: рецепт выше работает и без неё.

**2. ВЫВОД старых консольных утилит.** `type`, `findstr`, `more`, `sort` и `fc`
льют в консоль **сырые байты файла** через `WriteFile`, минуя юникодную конверсию
консоли: консоль получает поток байтов UTF-8 и трактует его по своей странице
CP866 — `В тихом` превращается в кракозябры. Проверено на живой машине: префикс
`chcp 65001`, с которым приложение запускает каждую команду, на этот путь не
действует, — для UTF-8-файлов с кириллицей эти утилиты ненадёжны в принципе.

Префикс при этом не бесполезен: он выставляет кодовую страницу вывода консоли в
65001, и запущенный следом дочерний `powershell.exe` наследует её как
`[Console]::OutputEncoding = UTF-8` — поэтому вывод рецепта выше отображается
чисто без явной настройки кодировки внутри команды.

Если вывод с кириллицей всё-таки показался кракозябрами (например, у `type файл`),
прочитайте файл через PowerShell — этот путь от кодировки консоли не зависит:

```text
powershell -NoProfile -Command "Get-Content файл -Encoding UTF8"
```

## Остановка, ограничения, watchdog

- **■ Стоп** убивает всё дерево процессов: Windows — `taskkill /pid N /T /F`
  (отдельно от pty.kill, иначе ConPTY переживает детей), POSIX — SIGTERM группе
  процессов (`-pid`, процесс запущен лидером группы), через 2 секунды SIGKILL.
  Скрипт с `subprocess` не оставляет сирот. При выходе из приложения
  (`before-quit`) дерево активной сессии убивается так же.
- **Watchdog бездействия** (настраивается, по умолчанию 600 секунд, `0` —
  выключен): любой вывод или ввод сбрасывает таймер — долгая компиляция с
  прогрессом не прерывается, а программа, молча ждущая пользователя, не висит
  вечно.
- **Кольцо вывода 4 МБ** на сессию: при переполнении процесс останавливается
  (пометка «вывод превысил лимит»), в отчёт попадает хвост — ошибка важнее начала.
- **Журнал ввода 256 КБ** на сессию: в pty ввод уходит целиком, а отчёт при
  обрезании честно помечает «ввод показан не полностью». Ввод из предложения
  (тело `&RUN:`/`&CMD:`) ограничен 64 КБ ещё на входе.
- **Окно досбора вывода** (150 мс после события выхода): pty сообщает код возврата
  раньше, чем последние байты доезжают по трубе (на Windows ConPTY отдаёт код
  раньше последнего кадра). Без досбора быстрая команда с ошибкой показывала
  только «Код возврата: 1» без текста ошибки. Если вывод так и не пришёл,
  терминал печатает явную пометку `[вывода нет: псевдоконсоль ничего не передала…]`.
- На время сессии наблюдение за папкой проекта приостанавливается (`pauseWatcher`):
  компиляция и запуск создают файлы (`.ide_build`, `__pycache__`), и наблюдатель не
  должен захлёбываться. По завершении наблюдатель гарантированно возобновляется.

## Отчёт (runfmt)

`buildReport` собирает текст для вставки в чат: файл, команда, папка проекта, код
возврата, ввод и вывод. ANSI-коды (CSI, OSC, одиночный ESC) вычищаются — xterm их
рисует, а в чате они превратились бы в мусор. Управляющие символы C0 (кроме
табуляции и переводов строк) тоже: в журнале ввода не остаётся «следов» стрелок,
Backspace и уведомлений о фокусе (ConPTY режим 1004, xterm.js отвечает
`\u001b[I`/`\u001b[O` на каждый клик). Ввод нормализуется к LF. Вывод обрезается до
хвоста ~200 КБ с пометкой. Тело отчёта оборачивается в ```-ограждение для чата;
если сам вывод содержит ```, ограждение повышается до четырёх backtick.

В строке «Команда» инструмент показывается коротким именем (`python -u test.py`),
а не полным путём из PATH: путь виден в настройках, а в чате он шумит. Двухшаговый
план показывается стрелкой: `javac … → java -cp .ide_build/classes Main`.

## Классификация опасных команд

Уровень риска карточки `&CMD:` — максимум по сегментам командной строки (разбивка
по `&&`, `||`, `|`, `;`, `&` и переводам строк с учётом двойных кавычек). Списки —
данные в `src/runlangs.js` (общие для main и renderer): безусловная опасность
(удаление, форматирование, планировщики, обёртки вроде `mshta`/`rundll32`,
`eval`/`iex`), опасные флаги (`--force`, `-rf`, `--no-preserve-root`, `--hard`),
подкоманды git (push/clean/reset/rebase/filter-branch — опасность; commit/merge/
stash/checkout — осторожно), `reg add/delete`, `sc create`, `net user`,
закодированные команды (`-enc`), установка пакетов (pip/npm/dotnet с изменяющей
подкомандой), сеть и скачивание, управление процессами. Красный уровень требует
явного подтверждения; жёлтый показывает бейдж. Расширить правило — дописать строку
в список.

## node-pty: загрузка и отказы

Нативный модуль грузится лениво и с try/catch: на платформе без пребилда или при
битой установке всё остальное приложение обязано работать, а ошибка всплывёт в
момент первого запуска понятным тостом, а не падением main. В packaged-сборке
node-pty распакован из asar (`asarUnpack`).
